## Context

Job hunting currently means maintaining a spreadsheet by hand: companies, roles, status, salary research, WLB signals — time-consuming and error-prone, and the "soft" research (comp, AI-proofness, work-life balance, interview prep tips) requires manually digging through Glassdoor, Reddit, levels.fyi, etc. The goal is a personal CLI tool that owns this whole pipeline: track companies/roles, auto-enrich them with researched data (including from login-gated sites, via your own authenticated session), score/sort by what actually matters to you, and surface a few decision-support features (staleness, duplicates, recruiter follow-up nudges, reapply cooldowns) so nothing falls through the cracks.

This is a greenfield project (repo currently contains only `IDEA.md`). Design was worked out over several rounds — key decisions and why:

- **TypeScript/Node + SQLite (WAL mode)**, data under `./.data/` (gitignored). SQLite is fully ACID and, in WAL mode, supports concurrent readers alongside one writer — which is what lets the CLI and daemon share the DB file safely with no IPC protocol needed.
- **Enrichment goes through the `claude` CLI, not the Anthropic API directly** — standalone `.sh` scripts under `src/enrichment/scripts/` call `claude -p "<prompt>" --output-format json`, so no API key management and prompts are editable independent of app code.
- **Login-gated research (Glassdoor, etc.) uses Playwright with a dedicated persistent browser profile** — a one-time `cm auth login-browser` command opens a visible browser against `.data/browser-profile/`, you log in manually once, and all later fetches from that profile run headlessly, already authenticated. (Ruled out `claude-in-chrome`: it requires an interactive session with the extension bridge attached and is explicitly disabled under API-key/headless auth — confirmed via research, not assumption.) **Status as of 2026-09-10: this path has never worked end-to-end and is deprioritized.** `sources.json` ships with `company_wlb.urlTemplate: null`, so the WLB job always short-circuits with a `company.wlb_skipped` event and never opens a browser; and Google sign-in inside an automation-controlled Chromium is refused by Google ("This browser or app may not be secure"), so `cm auth login-browser` can't complete a Google-backed Glassdoor login. Don't build on it. See "Backlog" in Phase 2 for the intended replacement (public-source WLB signal via the research script).
- **Phase 2 (2026-09-10) reframes data handling as a build system** — raw fetched pages are immutable snapshots on disk, every model-derived value records the input hash and recipe version it was computed from, staleness is a hash comparison done lazily on read, and `--force` means only "take a new snapshot". The model is called only when an input actually changed. Rationale and mechanics are in the "Phase 2 — memoized data pipeline" section; this bullet exists so nobody reading the original design above assumes the fetch-and-extract-every-time behaviour of steps 7-12 is still intended.
- **Decoupled architecture**: CLI (thin client) → writes rows to SQLite → Daemon (long-running, auto-started on demand) owns a worker pool that polls SQLite for jobs. The database *is* the only IPC channel — no socket/RPC layer. This gives real separation of concerns without inventing a wire protocol nobody needs yet.
- **Multi-topic job queue in one SQLite table** (not separate physical queues) — a `topic` column plus per-topic worker concurrency lets cheap/fast jobs (notifications) run without waiting behind slow/expensive ones (enrichment, which is serialized to 1 concurrent job since Playwright owns one real browser).
- **Scope**: full CRUD + status tracking + enrichment (comp, equity, IPO status, remote/EU, AI-proofness, WLB) + on-demand cited "tips" research + lightweight recruiter-contact tracking + weighted priority scoring (including a manual per-company preference rating) + pipeline digest/staleness flagging + reapply-cooldown + hard-block duplicate detection. **Explicitly out of scope for this build**: CV.md generation and PDF rendering (user will do this once they supply their experience data — deferred), and periodic/scheduled runs via launchd (refresh/discover are manual-only for now, launchd wiring is a later phase once proven).

## Data model (SQLite)

- **companies**: id, url, name, description, preference_rating (-2..2, manual), connections (freeform text, manual — referral/who-you-know), ipo_status, ai_proof_score, ai_proof_notes, wlb_score, wlb_notes, last_enriched_at, created_at, updated_at.
  *(AI-proofness and WLB live on the company, not the role — they're properties of the employer, not the individual posting; this also lets Tips research be cached and reused across roles at the same company.)*
- **roles**: id, company_id, url, title, description, status (`new|todo|applied|interviewing|success|denied|skip`, unrestricted transitions — this is a personal tool, not a shared workflow, so no state-machine enforcement, just a well-defined value set), status_changed_at, reapply_after (nullable, auto-set to +1 month on `denied`, editable), salary_min, salary_max, equity, remote_eu, priority_score (computed), closed_at, last_checked_at, last_enriched_at, created_at, updated_at.
- **role_status_history**: id, role_id, from_status, to_status, changed_at, context (free text — the IDEA.md requirement that every action carries timestamp + context).
- **role_references** (named so because `references` is a SQL keyword): id, role_id, type (`cv|application_answers|cover_letter|other`), file_path, notes, created_at. Files live under `.data/files/<role-id>/`. Table exists since migration 0001; no CLI command writes to it yet (Backlog).
- **tips**: id, scope (`company|role`), company_id (nullable), role_id (nullable), content (markdown), sources (JSON array of `{url, title}` — every source cited, no exceptions), generated_at.
- **recruiter_contacts**: id, role_id, recruiter_name, contacted_at, channel (open text), link, notes, responded_at (nullable — null + `contacted_at` older than `settings.recruiter_nudge_days` (default 7) = overdue for follow-up).
- **interview_notes**: id, role_id, stage (freeform), notes, occurred_at, created_at.
- **events**: id, entity_type, entity_id, type, context (JSON), occurred_at — immutable audit trail for every action and periodic-job run, per IDEA.md's debugging requirement.
- **notifications**: id, event_id (fk), channel, message, delivered_at, acknowledged_at (nullable) — the mutable "inbox" layer on top of the immutable events log; `cm inbox` reads unacknowledged rows.
- **jobs**: id, topic (`enrichment|notification|refresh|discovery|tips`), payload (JSON), status (`pending|running|done|failed`), priority, attempts, available_at (retry backoff), error, created_at, updated_at.
- **operational_logs**: id, occurred_at, severity (`debug|info|warn|error`), outcome (`started|succeeded|failed|retried|skipped`), component, action, job_id (fk, nullable), entity_type/entity_id (nullable, inferred from the job payload — see Step 11), context (JSON, sanitized), error (sanitized). Distinct from `events`: `events`/`notifications` are user-facing (an inbox, a per-entity audit trail); `operational_logs` is an internal diagnostics stream for every CLI/daemon/job action, whether or not it's something a user would want surfaced.

Phase 2 adds two tables — `page_snapshots` and `derivations` — and drops `roles.priority_score`; they're specified in the Phase 2 section, not here, so the original data model above stays readable as the baseline.

Config files (`.data/config/*.json`, auto-seeded with defaults on first read by the loaders in `src/config/*.ts`, user-editable, not DB rows since they're low-volume and meant to be hand-tuned):
- `preferences.json` — single profile: title/keyword match, seniority, remote+EU required, min salary floor. Used by `discover` to filter fetched roles.
- `scoring.json` — weights for the priority formula: `comp_fit, remote_eu_match, ai_proof, wlb, preference_match, company_preference`. Ships with equal weights as placeholders — tune once real enriched data exists.
- `settings.json` — `recruiter_nudge_days: 7`, `stale_days: 14`, `reapply_cooldown_months: 1` (currently read but unused — `setStatus` hardcodes one month; Backlog). Phase 2 adds `page_refresh_days` (per-kind snapshot refresh policy) and `claude_max_budget_usd`.
- `sources.json` (under `src/enrichment/`) — per data-source recipe: name, example/template URLs, `requires_login: boolean`, extraction instructions. Seed with placeholder entries for comp (levels.fyi/Glassdoor), WLB/tips (Glassdoor/Reddit/Blind) — you'll supply real example URLs to tighten these and stop Claude from over-browsing.

## Architecture

**CLI → DB → Daemon → Worker pool → Enrichment scripts → `claude` CLI / Playwright**

1. CLI commands (`cm companies add`, `cm roles add`, etc.) write directly to SQLite: create the entity row, insert one or more `jobs` rows, then check `.data/daemon.pid` — if the daemon isn't alive, spawn it detached (`{ detached: true, stdio: 'ignore' }`, `.unref()`), then return immediately. No waiting.
2. The daemon owns a **worker pool manager** with per-topic concurrency: `enrichment: 1` (Playwright/Chrome-bound, must serialize), `notification: 3`, `refresh: 1`, `discovery: 1`, `tips: 1`. Each worker polls for a claimable job with a single-statement claim (`UPDATE jobs SET status='running' WHERE id = (SELECT id FROM jobs WHERE topic=? AND status='pending' AND available_at<=? ORDER BY priority DESC, created_at ASC LIMIT 1) RETURNING *`), processes it, and marks `done`/`failed` (with backoff + retry) on completion — writing an `events` row either way.
3. **Enrichment handler**: looks up the relevant recipe in `sources.json`. If `requires_login`, fetches via `browser/profile.ts` (Playwright persistent context against `.data/browser-profile/`, headless); otherwise a plain HTTP fetch. Page content is piped into the matching `.sh` script, which calls `claude -p` with the content + recipe instructions and returns structured JSON (comp, equity, remote/EU for roles; IPO/AI-proof/WLB for companies). Structural fetch (name/description/title on `add`) follows the same shape but runs first/fast, separately from the "full enrichment" (comp/remote-EU/AI-proof/WLB) job that follows it automatically.
4. **Tips** are *not* part of automatic full enrichment — triggered on demand via `cm tips <role-id>`, which enqueues a `tips` job. Company-level findings are cached (checked via `tips.scope='company'` + `generated_at` freshness) and reused across roles at that company; role-specific findings layer on top per role.
5. **Notification jobs**: enqueued by other handlers (e.g. refresh detecting a closed role) with a message payload; the notification handler writes an `events` + `notifications` row and dispatches to the terminal digest and/or a macOS banner (`osascript`).
6. **`cm auth login-browser`**: launches Playwright non-headless against the persistent profile dir, waits for you to close the window, done. Re-run whenever a session expires.

## Feature-specific mechanics

- **Priority score**: `priority.ts` computes a weighted sum of normalized dimensions (comp fit vs. your target, remote+EU match, company AI-proof score, company WLB score, preference-profile match fraction, and the manual `company.preference_rating`), using `scoring.json` weights. Recomputed whenever a role's enrichment data, its company's enrichment/preference data, or the preference profile changes. Computed for every role regardless of status (cheap), but `cm roles list`'s default view filters to active statuses so terminal-state roles don't clutter sorting.
- **Duplicate detection**: on `cm roles add`, normalize company+title (case-insensitive/trim) and check against existing roles; on a match, hard-block and require `--force` to add anyway (deliberately strict — a bad add would cascade into enrichment jobs, notifications, etc. for a phantom role).
- **Reapply cooldown**: marking a role `denied` auto-sets `reapply_after = now + 1 month`, editable via `cm roles set-reapply`.
- **Pipeline digest (`cm status`)**: counts per status, roles with `status_changed_at` older than `settings.stale_days` (14, default) flagged as stalled, recruiter contacts overdue per `recruiter_nudge_days`, and roles with an upcoming/passed `reapply_after`. All computed at query time — no background "nudge" job needed yet, since there's no scheduler running unattended.
- **Interview notes**: `cm interview-note add <role-id> --stage "..." --notes "..."` — freeform, timestamped, feeds future Tips generation qualitatively (you read your own notes when re-researching similar roles).
- **Recruiter tracking**: intentionally minimal — `cm recruiters ping <role-id> --name --channel --link`, `cm recruiters respond <contact-id>`, `cm recruiters list --overdue`.
- **Refresh/discover**: both manual-only commands (`cm refresh`, `cm discover`) for now — `refresh` re-checks existing role URLs for closure (via the same fetch mechanism as enrichment) and enqueues notification jobs on closure; `discover` only scans career pages of companies you've already added, filters against `preferences.json`, and applies the same duplicate check before creating candidate roles. Periodic/launchd scheduling is a deliberately deferred later phase for both.

## Delivery process — commitable steps

Work proceeds one step at a time, each a separate commit. For each step:

1. Write that step's tests (first or alongside).
2. Implement until the tests are green.
3. Send the uncommitted diff to an independent review agent (the `code-review` skill/subagent — not a context-sharing fork, so the review isn't anchored to the same assumptions as the implementation).
4. Address every comment the reviewer raises — fix, or, if a comment is wrong or out of scope for this step, say why in the commit and move on rather than silently dropping it.
5. Re-run the tests, then commit.

A step should not start until the previous one's tests pass *and* has been through this review — later steps depend on earlier ones' schema/plumbing, so defects compound if they're not caught early.

**Test framework**: [Vitest](https://vitest.dev) — fast, TS-native, good `child_process` support for black-box CLI testing.

**Testing philosophy** (applies to every step below):
- **Primary: user-perspective tests.** Invoke the actual built `cm` binary via `child_process` against an isolated temp `.data` directory (env var override, e.g. `CM_DATA_DIR`), assert on stdout/exit code and resulting DB state. This is what "tests for that step" means by default — a scenario a user would actually run.
- **Secondary: unit tests** for pure-logic modules where a full CLI round-trip would be overkill or non-deterministic — scoring math (`priority.ts`), duplicate-match normalization, staleness/overdue date math, migration schema shape.
- **External dependencies** (`claude -p`, live websites, real browser login) are the one place black-box CLI tests become non-deterministic. Rule: fetch/network inputs are served from **local fixtures** (a tiny fixture HTTP server serving canned HTML, or a fixture profile directory with pre-seeded cookies) so tests are deterministic and CI-safe; only the `claude -p` extraction call itself is a live dependency in steps 7-10, and those steps should still assert on the *shape* of the result (fields present, sources array non-empty) rather than exact wording. A handful of steps also carry one **manual verification note** for things no automated test can cover (an actual human login flow) — these are called out explicitly, not silently skipped.

## Phase 2 — memoized data pipeline (build-system model)

Decided 2026-09-10 after a whole-repo review of the finished steps 1-14. The original build fetches and re-extracts on every `add`/`rerun-enrichment`, sends raw HTML (up to 500 KB) to `claude -p` with no model or tool restriction, and keeps nothing of what it fetched. That is expensive (the `claude` subscription ran dry mid-use), opaque (nothing on disk to inspect when an extraction goes wrong), and non-idempotent. Phase 2 changes the data-handling model. Everything else — CLI shape, job queue, events, logs, daemon — stays.

### The model

Treat the system like `make`. There are **sources**, **rules**, and **outputs**. Nobody ever asks "is this stale?" in the abstract; the only question is "does this output's recorded input key still equal the current input key?"

1. **Raw data is a source: immutable, append-only snapshots on disk.** Every fetch of a URL writes `.data/pages/<sha256(url)>/<fetched-at-iso>.html` plus a `page_snapshots` row (url, fetched_at, http_status, content_hash, byte size, error). Fetching again adds a snapshot; nothing is overwritten. A snapshot whose `content_hash` equals the previous one's is recorded as a row (so "we checked, unchanged" is visible) but reuses the previous file. Snapshots are what `cat` and `diff` operate on when debugging.
2. **Deterministic derivations run first and are free.** HTML→text (`<fetched-at>.txt` beside the HTML), `<title>`/`og:title`, canonical URL, closure-phrase regex matching, HTTP 404/410. These are plain TypeScript, run in-process, never touch the model. They cover the common cases; the model only sees what they can't decide.
3. **Model-derived data is an output keyed by its inputs.** One `derivations` row per (entity, kind), upserted, recording: `source_key` (the content hash of the snapshot text it read, or for web-research kinds the sha256 of the JSON context it was given), `recipe_version` (sha256 of the `.sh` script file that produced it — so editing a prompt invalidates its outputs automatically), `model`, `cost_usd` and token counts from the `claude` envelope, `computed_at`, `job_id`. The field values themselves stay on `companies`/`roles`/`tips` as today; `derivations` is the bookkeeping beside them.
4. **Staleness is a comparison, done lazily on read.** A derivation is stale when the newest snapshot's text hash (or the current context hash) ≠ its `source_key`, or the script's current hash ≠ its `recipe_version`. `cm roles show`/`cm companies show`/`cm roles list` compute this per field group, print the existing value with a `(stale)` marker, and enqueue a recompute job — **debounced**: no enqueue if a pending/running job for the same (entity, kind) already exists. No eager recompute pass, no dependency graph, no invalidation cascade. Stale data is visible rather than silently wrong, and it heals itself the next time the daemon runs.
5. **Snapshot refresh is a policy, separate from staleness.** "Is the derived value consistent with the raw data?" is the hash check above. "Is the raw data old enough that I want a new snapshot?" is `settings.page_refresh_days` (per kind: role pages, company pages), consulted by `add` on an already-known URL and by `rerun-enrichment`. Keep these two concepts apart in code and in docs. **Corrected in Step 16: `refresh` does *not* consult it.** "Has this posting closed?" is a question about the live page by definition — answering it from a three-day-old snapshot reports a closed role as open, stamps `last_checked_at` as though we had looked, and (since the closure judgement still runs) costs the same as a real check. A closure check always takes a new snapshot.
6. **`--force` means exactly one thing: take a new snapshot now, ignoring `page_refresh_days`.** It never means "overwrite derived data" — a new snapshot with a different hash makes every derivation on that entity stale by definition, and lazy recompute does the rest. `add` on an existing URL without `--force` is a no-op that prints the existing entity (idempotent). `rerun-enrichment` becomes an alias for `--force` semantics and may be removed. **Corrected in Step 17:** `force` *also* bypasses the freshness skip on the structural kinds. The reasoning above holds only when the re-fetched page differs; when it doesn't, the new snapshot has the same `text_hash` and the recompute skips — leaving no way whatsoever to redo an extraction the model simply got wrong, while the command still reports "Re-enrichment queued". A user asking to re-fetch and re-enrich is asking for the value to be recomputed.
7. **Priority score is computed on read, never stored.** It is pure and cheap, and it was the only multi-input derivation; not storing it removes the hardest node from the graph. `roles.priority_score` is dropped (migration); `listRoles --sort priority` sorts in memory.
8. **The model is called only when a key changed, on text not HTML, with the cheapest adequate model, with no tools it doesn't need.** Extraction scripts (`extract-*.sh`): `--model haiku --tools ""`. Research scripts (`research-*.sh`): `--model sonnet --tools WebSearch`. All scripts: `--setting-sources ""` (no user hooks/settings inside the extraction session), `--max-turns` (1 for extraction, small for research), `--max-budget-usd` from settings, spawned with `cwd` set to an empty scratch dir. Fetched page content is untrusted input; these flags are what keep an instruction embedded in a job posting from reading `.data/` or searching the web with it.

### What does NOT change

- CLI command set and output style; job queue/topics/concurrency; `events`, `notifications`, `operational_logs`; daemon auto-start; the `.sh`-scripts-call-`claude -p` design; test philosophy (black-box CLI against a temp `CM_DATA_DIR`).
- The chain structural → research → (wlb) per entity still exists; it just becomes "recompute what's stale for this entity" instead of "always run everything".

### Data model additions

- **page_snapshots**: id, url, url_hash (sha256 of the URL as given), fetched_at, http_status (nullable on network failure), content_hash (sha256 of the raw body; nullable on failure), text_hash (sha256 of the derived text), bytes, html_path, text_path, error (sanitized, nullable). Index on (url_hash, fetched_at DESC). "Latest snapshot for URL" = first row of that index.
- **derivations**: id, entity_type (`company|role`), entity_id, kind (`company_structural|role_structural|role_research|company_research|company_wlb|role_closure|tips_company|tips_role`), source_key, recipe_version, model, cost_usd, input_tokens, output_tokens, computed_at, job_id (fk, nullable). UNIQUE (entity_type, entity_id, kind). Upsert on every successful compute.
- **roles.priority_score**: dropped (Step 19).
- **settings.json** gains `page_refresh_days: { role: 3, company: 30 }` and `claude_max_budget_usd: 0.50` (per call).

## Phase 3 — measurement + conversational interface

Decided 2026-09-14, from use rather than review. Two problems with the finished tool, in the user's
words: *"it's unclear how to use the command from CLI alone — chatting with an agent is MUCH
easier"*, and *"I want to measure the time it takes... also how many tokens it costs"*. The mental
model they reach for is a **funnel**: a set of opportunities, each moving through stages.

### The decisions, and why

**Interface: an MCP server, not an in-CLI natural-language router.** Both were costed. A router
(`cm "mark the Stripe role applied"`) means building and maintaining prompt-to-action translation:
~2.5K tokens of tool schema per call, ~$0.003 on Haiku 4.5, or ~$0.0006 with the tool block cached —
against $0.13 for one `roles add`, so cost was never the objection. The objection is that an MCP
server gets the same thing for **no router at all**: the host model does the translation, and the
MCP tool list *is* the constrained action set. Less to build, less to maintain, nothing to tune.
The in-CLI router remains the right answer only for driving the tool from a bare terminal with no
agent session; it is in the Backlog, not here.

**Forcing a subset of actions** — the user's open question — has three layers, and only the third is
enforcement. Model-side: `tool_choice: {type: "any"}` compels a tool call rather than prose, and
`strict: true` makes arguments schema-valid (note: forced tool use returns 400 on Fable 5.1 /
Mythos 5.1, so a router would have to pin its model). Via the CLI instead of the SDK,
`--json-schema` gives the same validation with no API key, consistent with this project's existing
design. **But the actual guarantee is the dispatcher**: a whitelist in TypeScript, with read-only
actions separated from mutating ones. Model constraints produce well-formed output; they do not
produce *correct* output. With MCP, the tool registry is that whitelist by construction.

**No MCP SDK.** `@modelcontextprotocol/sdk` is official and correct, but installs 91 packages / 26 MB
— including express, hono, cors and jose — for what is, over stdio, newline-delimited JSON-RPC 2.0
with four methods. This project has 36 packages total and has been deliberate about that. The server
is hand-rolled with no new dependencies, and the risk that buys (protocol drift) is paid for by
verifying against the **real client** via `claude mcp add`, not only against our own test double —
the same discipline that caught `--tools "WebSearch"` silently disabling search in Step 18. If
protocol drift ever does bite, swapping in the SDK is a contained change behind `src/mcp/`.
